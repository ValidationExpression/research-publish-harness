# JavaScript / TypeScript 开发规范

## 适用范围与项目约定

1. 本规则以兼容标识 `frontend` 覆盖通用 JavaScript / TypeScript、Web 资源和 Node.js 项目，不要求引入 Web 框架或将 JavaScript 迁移为 TypeScript。
2. 必须遵循项目现有运行时、包管理器、格式化和检查配置；模块系统必须与构建及运行配置一致，ESM / CommonJS 互操作需在明确边界处理。

## 代码组织与架构边界

1. 按业务能力和副作用边界组织模块，避免循环依赖与隐式全局可变状态；公共导出应保持最小且稳定，不强制固定目录分层。
2. 若项目使用 Web UI，必须明确组件、状态和请求逻辑的所有权，优先复用已有组件及请求封装；状态优先就近管理，共享状态须有明确更新入口，不强制引入状态库。

## 类型、命名与可读性

1. 若项目使用 TypeScript，必须启用严格类型检查；存量迁移需记录暂缓范围与收敛计划，禁止通过未校验的 `any` 或类型断言绕过边界，外部未知数据应先按 `unknown` 收窄。
2. 公共接口与核心数据结构应明确类型契约；必须在运行时校验网络响应、配置、存储和用户输入，静态类型不能证明外部数据有效。
3. 命名与导出风格遵循项目及生态惯例，避免无含义缩写；复杂条件和数据转换应拆为可测试的命名操作。

## 错误处理、并发与资源管理

1. Promise 拒绝必须被等待、返回给调用方或显式捕获；禁止无错误出口的悬空异步任务，错误处理必须保留原因并区分取消与真实失败。
2. 异步请求必须明确超时、取消和过期结果处理；定时器、事件监听、订阅与连接必须在所属生命周期结束时清理，避免竞态覆盖新状态。
3. 并发任务必须设置合理上限并说明部分失败策略，禁止对不受控输入无限展开并行任务。

## 依赖、安全与数据访问

1. 必须提交并审查项目包管理器对应的锁文件，CI 使用锁定安装；禁止混用包管理器造成依赖漂移，新增依赖先检查现有能力。
2. 若项目使用 Web DOM，禁止将不可信内容直接传给 `innerHTML` 等注入入口；普通文本使用安全文本接口，确需富文本时使用项目认可的净化策略，并按 HTML / URL 等上下文校验和编码。
3. 若项目使用浏览器客户端，禁止打包服务端密钥；前端权限控制只改善体验，服务端必须独立执行身份与权限校验。

## 测试与工具链

1. 必须使用项目现有测试、lint、格式化、类型检查和构建命令验证变更，覆盖数据边界、异步失败、取消和关键行为；不得为本规则更换工具链。
2. 若项目使用 Web UI，交互变更必须有组件或关键用户路径测试，并验证语义化结构、键盘操作、焦点管理和可访问名称，不能只以快照证明可用性。

## 条件式框架规则

1. 若项目使用 Node.js，必须避免在请求热路径执行阻塞事件循环的同步 I/O 或重 CPU 运算，按项目能力使用异步接口、流背压或隔离任务，并验证超时和退出时的资源释放。
2. 若项目使用 React，必须遵守 Hook 调用规则；Effect 仅用于外部同步并声明正确依赖，需要撤销副作用或释放资源时必须返回清理函数；列表 key 必须稳定，避免复制可推导状态。
3. 若项目使用 Vue，必须保持响应式数据流明确，禁止直接修改传入的 props；监听器和外部订阅须清理，复用逻辑遵循项目现有组合方式。
4. 若项目使用 Angular，必须遵循现有依赖注入和组件边界；订阅须绑定生命周期或显式退订，不得绕过模板安全机制处理不可信内容。
5. 若项目使用 Next.js 或 Nuxt，必须明确服务端与客户端边界、缓存范围及失效策略；服务端凭据不得进入客户端包，用户私有数据不得进入共享缓存，并验证服务端渲染与 hydration 一致性。
